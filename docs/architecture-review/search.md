# Search and discovery architecture

## Index design

Search uses SQLite FTS5 virtual table `repos_fts` with Porter stemming and Unicode 6.1 tokenization. Indexed fields are:

- `full_name`;
- `owner`;
- `name`;
- `description`;
- `language`;
- `license`;
- serialized topics;
- latest README text, truncated to the first 50,000 characters.

`repo_id` is stored unindexed to join results back to `repos`. Category, summary, homepage, source file names/content, release text, dependency data, and event payloads are not searchable.

## Index lifecycle

Indexing is explicit application code rather than triggers:

- insert initial document after discovery;
- delete/reinsert after enrich/refresh;
- delete/reinsert after a changed README snapshot;
- migration v6 backfills existing rows;
- doctor can compare FTS/repository counts and rebuild.

Because there is no transactionally enforced trigger, a crash or unhandled write path can leave FTS stale. Delete/reinsert is simple but rewrites a whole document—including up to 50,000 README characters—for small metadata changes. `docs/ROADMAP.md` correctly lists incremental FTS as future performance work.

## Query construction

User text is tokenized/escaped into prefix terms joined with AND semantics. SQLite returns BM25 rank and HTML snippets with mark tags. With no explicit sort, FTS rank drives ordering; selected feed/sort modes override relevance.

Filters join or correlate current tables for language, discovery source, dates/year, enrichment/deletion state, archive/README/release presence, and star/fork thresholds. Recently archived/released sorts use correlated subqueries. Pagination is offset-based.

## Search UX

Search is available on home and via `/api/search`; birth feed uses the same query/filter parser. Results show highlighted snippets through `RepoListItem`. Language choices come from distinct current repository values. Query string preserves most filters and page state.

Absent UX capabilities:

- autocomplete or query suggestions;
- spelling correction/fuzzy matching;
- synonyms or ecosystem aliases;
- query history/saved searches;
- result facets/counts beyond available languages/global stats;
- semantic search;
- source-code search;
- explain-why-this-result UI;
- relevance feedback or click analytics;
- zero-result fallback;
- stable cursor pagination.

## Discovery feeds and ranking

The repository query layer supports newest discovered/created, popularity, recently archived, recently released, deleted, and legacy feed mappings. Birth feed defaults to newest discovery. Related projects are a separate FTS/topic heuristic described in the intelligence review. Trend feeds use metrics/events, not FTS.

There is no random feed, editorial ranking, personalized ranking, diversity control, freshness/popularity blend model, abuse handling, or reproducible ranking version.

## Performance characteristics

- FTS is appropriate for local single-node metadata/README search and avoids an external service.
- README text makes the index and delete/reinsert operations much larger than metadata-only search.
- AND-prefix queries can be overly restrictive for multiple topics.
- Offset pagination cost grows with deep pages.
- `strftime` year filtering applies a function to timestamp columns, reducing normal index usefulness.
- Correlated archive/release existence/sort expressions can execute per candidate row.
- Result projection adds N+1 archive badge and ZIP URL queries.
- Synchronous FTS/query execution blocks the Node event loop during each request.
- No production dataset exists here, so selectivity, p50/p95 latency, index size, and maximum practical repository count are unknown.

## Search correctness and security

FTS snippets are rendered using `{@html}`. The expected HTML is generated by SQLite with controlled mark tags, but component code does not sanitize it. Search query construction must remain the only source of snippet markup; tests should prove stored README/description HTML cannot escape the mark wrapper.

No query timeout or complexity budget exists. FTS escaping reduces syntax errors, but numeric pagination/filter validation is weak. There is no public rate limit, so search can be used to create database/CPU load.

## Search tests

There is no dedicated FTS query/relevance/security test suite. Migration/doctor indirectly cover FTS creation/counts, and other repository tests use temporary SQLite, but missing cases include token escaping, Unicode, stemming, prefix semantics, snippets/XSS, filter combinations, relevance stability, deep pagination, rebuild equivalence, and production-sized query plans.
